# FreeLP implementation and verification

FreeLP uses injected wallets and configured RPC endpoints for application data and signing. Its initial 11 mainnets are an explicit FreeLP default set; other viem mainnets can be enabled in Settings. Names, native-token metadata and default endpoints come from viem. Catalog membership does not prove deployment or EVM-version compatibility. RPC overrides are empty by default. Disabled chains stay disabled, including when all chains are off. Native currencies use the zero address, and imported metadata is unique by chain ID and normalized token address.

Contract checks verify the exact bundled runtime, with Core-bound immutable slots filled rather than ignored. RPC failures, missing contracts, and incompatible code are distinct states. Artifact imports require a clean pinned source checkout and verify metadata source hashes and compiler settings before replacing any artifact.

Token selection automatically discovers pair-specific registered pools through PoolKeyIndex using bounded pages on one block. These real configurations replace static fee cards; Advanced exposes custom fee, type, spacing and extension editors. Pool browsing is available before manager deployment, while deposit controls require verified Core, PoolKeyIndex, FreeLP and FreeLPDataFetcher code. Selecting a pool loads its current state through the data fetcher. Liquidity and selected range share one section, with paired token bars, exact data tables, drag selection, keyboard price/tick fields, zoom and centered range-width presets. Initial price appears only for a new pool. Numeric URL parameters snap for display without rewriting the incoming URL.

Pinned @ekubo/sdk math calculates deposit amounts locally. `evmLiquidity.ts` accounts for the EVM's intermediate flooring and the published SDK's token0 rounding issue; browser tests compare the results to simulated deposits in FreeLP. Amount changes do not request contract quotes. Balances and allowances are read through FreeLPDataFetcher and refreshed after transactions. Wallets supporting EIP-5792 can submit approval resets, approvals and deposits together, without requiring atomic execution. Sequential batch simulation precedes submission, and partial/pending batches are never automatically resubmitted. Separate approval buttons remain available. Withdrawals and fee collection use a manager multicall.

The current addresses and ABI are documented in [contract integration](contracts.md). The Deploy page prepares deterministic CREATE2 deployments for Core, PoolKeyIndex, FreeLP, and FreeLPDataFetcher. Deposits include an atomic native refund. Transaction simulation, wallet/account checks and receipt validation remain mandatory. Terms are informational and have no acceptance gate.

Validation covers SDK/contract parity, standard and batched ERC20 lifecycles, native-token positions, stableswap, collection, withdrawal with automatic NFT burning, URL handling, chain settings, token import and balance caching. Production checks also run Axe at mobile/desktop sizes, Lighthouse thresholds, and the packaged bunx/npx launcher. All routes and transaction code ship in one JavaScript bundle, so navigation needs no additional code fetches from IPFS. Reports are retained in CI.

The npm package is public. Launch with `bunx @ekubo/freelp@latest` or `npx @ekubo/freelp@latest`. CI publishes immutable IPFS previews and attaches their links to commits. IPFS information is kept out of the application itself.
